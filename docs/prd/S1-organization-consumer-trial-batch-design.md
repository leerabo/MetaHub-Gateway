# 组织开通与免登录使用者批次

日期：2026-09-09。用户补充优先于原路线图的默认入口设计；不撤销个人 Workspace 的既有数据和 API。

## 业务流程与所有权

- 新注册且没有任何 Workspace 的账号，首屏只保留“创建组织”主任务。账号安全、退出为次级操作。受邀账号和已有 Workspace 的切换流程保留。
- 组织创建者在同一事务成为 Owner，兼具组织管理权限，不授予任何 Platform 权限。
- 组织管理员配置真实 Provider、模型和路由，创建“使用者”，发放独立 MetaHub KEY。使用者有组织内稳定 ID、姓名、部门、状态，不要求 GlobalAccount、邮箱、密码或 Membership。
- KEY 的创建人是审计 actor，使用者是调用归属，两者不可混用。一个使用者允许多个 KEY。归属在服务端关联，不靠备注或客户端自报姓名推断。
- 禁用使用者要阻断关联 KEY 的后续调用；轮换保留归属及历史用量。KEY 被他人持有时只能证明凭据归属，不能证明现场操作人。
- 未来 SSO 使用 issuer + subject 的受控绑定关联已有使用者，不按邮箱或姓名自动合并，不自动授予后台管理权。
- 注册验证策略只由 SaaS Platform 管理；使用者、企业 SSO、Provider、路由和 KEY 属于组织。

## PRD-092 / 093 / 094 开通修订

当前 dev 免邮件注册不会创建 account_verifications，组织创建服务和旧 User 投影 trigger 因此拒绝创建。采用显式 local_workspace_creation_admissions：

1. GlobalSession、Origin、CSRF、幂等和账号状态检查不变。
2. 已验证账号继续原路径；未验证账号只在 environment=dev、平台邮件开关关闭、具有 local_registration_consents 时允许创建。
3. 在组织创建事务内写入绑定 workspace_id、tenant_id、account_id、registration_id、policy_revision 的不可修改授权记录。数据库验证创建者、绑定和本地同意来源完全一致。
4. User 投影 trigger 只为这个精确 Workspace 接受本地授权；密码 Hash、邮箱、凭据版本、一次性 claim 有效期等原校验保留。任何失败整体回滚。
5. prod/test、无本地同意来源、邮件开关开启均不开放未验证创建。邮件证明表保持不变；邀请接续仍要求原有验证。
6. 新增 SQLite/PostgreSQL 迁移；有本地组织授权事实后拒绝 schema down，不删组织或历史事实。

## PRD-094 / KEY 使用者修订

独立组织使用者目录、不可变 KEY 归属、组织管理员权限、归属 DTO 与 Gateway 鉴权已实现并发布到本地。不得复用要求密码的 legacy users 创建流程，不得以虚构邮箱建登录账号。按人用量筛选和财务报表尚未完成，不能把发放与停用验收当作费用闭环验收。

### 使用者实现合同（编码前补充）

- `workspace_consumers` 保存 tenant_id、consumer_id、display_name、department、active/disabled、revision、created_by 和时间。使用者没有账号、凭据、Membership 或登录权限。名称允许重复，稳定 ID 不可修改，不提供物理删除。
- `virtual_key_consumers` 用复合外键关联同租户 KEY 和使用者，KEY 归属不可修改或删除。仅创建新 KEY 时可绑定；旧 KEY 不补猜归属，历史技术 KEY 保持无使用者。换人必须签发另一把 KEY，不能把旧费用转给新人。
- `GET/POST /consumers` 和 `PATCH /consumers/{id}` 只允许企业 owner/admin 的 WorkspaceSession 或既有租户 admin；沿用租户权限及资源事务的逐次复核。列表分页，修改带 revision CAS。Platform/Support、普通 developer、机器凭据、其他租户和无会话全部拒绝。姓名、部门仅进入目录 DTO，不进入审计正文。
- `POST /virtual-keys` 新增可选 consumer_id。绑定员工时再次要求管理员并验证使用者 active；无绑定的技术 KEY 保留原权限合同。KEY DTO 只新增使用者 ID 和状态，不向技术角色输出员工姓名、部门。
- `POST /virtual-keys/{id}/rotate` 原子更换哈希和前缀，保留 KEY ID、归属、限制及历史用量；旧凭据立即失效，新明文仅返回一次。请求携带 `expected_revision`，数据库按单调递增的 `credential_revision` CAS，不能把可能重复的短前缀用作版本。并发旧版本只允许一次成功。已停用 KEY 或使用者不允许轮换。
- Gateway 每次认证连接权威目录。已绑定但不存在或停用的使用者一律拒绝；不以缓存、客户端 user/name/email 字段代替归属。停用不终止已进入处理的请求，后续鉴权拒绝。
- 用量本身已有 tenant_id + virtual_key_id，利用不可变归属可按人聚合且不重写旧账；后续用量筛选和财务报表必须沿该关联实现，费用状态/币种仍遵循原账务合同，不合并不同币种。
- 前端在 KEY 页面增加组织使用者目录、姓名/部门编辑及启停，发放时选择使用者。保留技术 KEY 与既有用户管理，不让员工身份进入登录用户表。所有写入沿用页面代次、重复提交保护和空间切换清理。
- SQLite 0148 / PostgreSQL 0155 成对迁移，登记租户删除清单；pristine down/up 可验证，有使用者或归属事实则拒绝回滚。开发先测受影响接口/鉴权，批次再测双数据库、浏览器、并发、性能、安全和必要回归。

### 真实浏览器开通批次补充设计

- 使用独立数据库、随机端口、独立浏览器 profile、真实 Control/Gateway 路由和当前源码字节；不复用用户 Cookie、不覆盖现有库、不调用外部模型。服务关闭后台 worker 生命周期，此证据只覆盖交互和同步接口，构建后发布另行验证。

- 第一轮自审：浏览器所有网络限于本批服务；使用同源部署分支且不伪造 fetch/响应。检查新账号首屏无企业或平台既有功能，组织 Owner 无平台权限，员工 KEY 无管理权限。若控制台仍请求 localhost 的旧地址，测试应失败而不是通过重定向掩盖。
