# S3 实际恢复执行设计

日期：2026-09-10。状态：两轮编码前自审完成，实施中，不代表 PRD-111 或 S3 整批完成。

本轮共享恢复执行层已实现并通过 47 个专项用例，含 9 个原生 PostgreSQL 用例。
独立记录：`docs/testing/PRD-111-actual-backup-restore-20260910.md`；持久任务与跨区切换接入尚未完成。

## 权威范围

Excel `01_PRD总表` 第 23 行要求数据库恢复、对象跨区副本、KMS 恢复、Gateway 路由切换、驻留约束、
防脑裂和季度恢复证据。Control RPO <= 900 秒、RTO <= 7200 秒，Gateway RTO <= 600 秒。
工作簿与旧 PRD 文档的“已完成”不足以证明这些要求；当前 DR handler 尚未调用实际恢复。
本设计延续 S3 共享执行与证据修订，不改试用服务、schema 0150 或已有用户数据。

## 共享执行合同

1. PRD-100 的备份执行层提供 PRD-111 使用的真实恢复事实。新快照记录版本化数据指纹，
   从同一快照读取 schema、Workspace/tenant 归属、账本、所有 Outbox 和配置数据。
   指纹只保留表名、行数和 SHA-256，不记录客户正文、账号邮箱、凭据或行值。
2. SQLite 从 online backup 的目标文件读取数据，不从仍在变化的源连接读取元数据。
   PostgreSQL 导出 REPEATABLE READ 快照，保持导出事务直到 pg_dump 完成；摘要与 dump 共用 snapshot。
   PostgreSQL LSN 仅作源观测标识，不声称单独 LSN 就是完整一致性证明。
3. 新 manifest 绑定指纹并参与 AES-GCM AAD；恢复时先验证 envelope、manifest 和明文内容摘要，
   再在隔离目标读取数据并重算指纹。少表、少行、修改记录、不同归属和不同配置水位均失败。
   旧 v1 备份保留可读能力，但不能伪造新一致性证明。
4. PostgreSQL 恢复前验证隔离目标，禁止源库别名、连接参数覆盖及已有应用数据目标。
   不执行 --clean 覆盖用户数据库；失败留下隔离目标供检查，不自动扩大清理范围。
   恢复子进程仅得到必要环境，错误仅输出固定代码。
5. 下一阶段将 PRD-111 的 run 固定绑定 recovery point、manifest、目标和 epoch，经 PRD-106
   持久外部等待执行。取消/超时/接管必须确认外部停止，不把进程内超时当作已终止恢复。
6. 切换之前重新核对审批、驻留与 writer fencing；数据恢复、对象副本、KMS 和实际路由/ACK
   证据分别产生，缺一项不能写入 verified 或 objectives_met。不能以备份对象读成功代替业务对象跨区复制。

## 第一轮自审：数据真实性与范围

- 原来恢复只检查 schema 和最多 100 条归属数量，同样数量的账本或配置损坏无法发现。
  新摘要读取实际行并绑定表结构、主键顺序与内容，恢复后独立计算；不是对 ID 或阶段名称做 hash。
- PostgreSQL 原来先提交元数据查询、后运行 pg_dump，会把两个时点拼成一份证据。
  导出快照事务必须保持存活，失败不能降级为无 snapshot 的 dump。
- 旧备份不能升级成未经采集的新证据。明确区分 v1 无指纹和新 manifest，保留旧恢复兼容性。
- 摘要读取包括敏感值，但日志、公开 DTO、异常和证据不包含原始行。摘要不能变成数据导出接口。

## 第二轮自审：安全、资源与生命周期

- URL 字符串不等不代表不同数据库。恢复目标身份要结合实际服务地址、端口和数据库名验证，
  禁止 URL query 覆盖 dbname/host 等身份，禁止对已存在应用对象的目标运行破坏性清理。
- 并发恢复不能共享目标。目标需要独占锁，且恢复期间锁归执行所有者持有；失败不能报告成功。
- 数据读取按主键分批，拒绝不支持的关键表结构，不能一次把全部账本加载进内存。
- 子进程 stderr 可能包含连接串或客户数据，仅用于内存中的返回码判断，不写入测试证据。
- 本轮只跑共享备份/恢复受影响测试和原生数据库专项，不重新跑前端或 S3 全套。
  云端对象复制、真实 KMS、路由切换、长稳和 Windows/Linux 完整批次门禁仍保持开放。

## 验证计划

使用独立临时数据库和合成数据。验证真实 SQLite 快照/恢复、同量记录篡改、丢行/丢表、归属漂移、
manifest 篡改、旧版本兼容、密文/错误敏感审计；原生 PostgreSQL 验证 MVCC 快照一致、真实 pg_dump /
pg_restore、非空目标拒绝及并发独占。分别记录执行范围，不能用 mock 对象服务声称云服务验收成功。

## 原生完整 schema 发现与补充自审

实际 pg_restore 失败于 `metahub_not_glob` 内部未限定 schema 的函数调用。pg_restore 的空 search_path
使兼容函数不可调用；部分 JSON 兼容函数还会吞掉异常返回 NULL，不能绕过约束来完成导入。

第一轮编码前审查：新增 PostgreSQL 0160，只为现有 0139 兼容函数固定
`pg_catalog, public, pg_temp` 搜索路径，不修改旧迁移、业务数据、函数正文或权限，不把 public 放在
pg_catalog 前。使用明确函数名白名单，不全库修改第三方函数。

第二轮编码前审查：在 bootstrap schema 保存每个函数原有 search_path；down 仅恢复该设置，
保留其他 proconfig。存在备份事实则禁止回退，避免丢失已恢复验证的前提。原生验证包含空路径执行、
完整 schema dump/restore 和 down/up；S3 迁移不得在试用库执行。

新 v2 manifest 同时绑定源数据库实际身份摘要；恢复不需要源库在线。v1 无此事实，仍需在线源身份
校验且不返回 v2 指纹。当前共享恢复只接受新建空目标，后续持久 runner 必须分配每次执行独立目标，
不能让定时备份复用已恢复的目标或重新引入 --clean。

现行完整 schema 的单事务 pg_restore 超出 PostgreSQL 默认共享锁容量。本地原生恢复集群使用
`max_locks_per_transaction=1024` 验证；部署恢复集群也需按完整 schema 和并发量配置该容量。
这是恢复目标的资源前提，不降低一致性要求，不自动修改用户的 PostgreSQL 配置。
