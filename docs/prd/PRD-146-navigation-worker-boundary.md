# PRD-146 导航数据库执行边界

S2 源码浏览器业务通过，但最终报告出现两次页面访问统计 503，旧报告另有导航 503。现有六个导航 transport endpoint 均为 async，却直接调用同步数据库服务。数据库锁等待、查询和提交会阻塞事件循环；这项代码事实足以修正执行边界，但尚不足以证明是全部 503 的根因。

## 第一轮自审

六个路由作为同域批次处理：导航、任务首页、高级工具列表、全局导航偏好、高级工具打开、页面访问统计。复用 Starlette run_in_threadpool，仅将完整同步服务调用移出事件循环；正文读取与解析仍在事件循环完成。原有依赖鉴权、来源/CSRF、未知参数拒绝、幂等键、If-Match、ETag 和 no-store 均不改变。

## 第二轮自审

连接继续由同步服务在同一工作线程创建、使用、提交并关闭，不在路由间传递数据库连接。不能将服务拆成多次线程调用，也不增加重试、放宽超时或吞掉数据库错误。定向测试用工作线程事件与异步 heartbeat 证明阻塞服务执行期间事件循环仍能推进，并检查失败正常传播；原数据库权限/幂等测试复用，联合浏览器报告必须检查所有非预期 5xx。

测试夹具的导航诊断同时覆盖页面访问统计，仅记录 SQLite 类型、错误分类和函数名，不记录异常正文、SQL、账号、Cookie 或请求正文。真实浏览器若仍出现 503，继续保留诊断，不将这项修订自动描述为根因修复。

## 旧导航偏好测试复核

候选 56 项回归有一项假定导航事件总数恒为 1；单独运行偏好测试或不运行此前 scheduler 测试时实际为 0。第一轮核对原 PRD-146 第 5/7.3 节：纯 UI 偏好仅写 command/audit，不产生 navigation changed。第二轮改为操作前记录事件数量，提交/重放/冲突后断言事件数量不变，继续断言恰好一条 command、正确 CAS/幂等和权限指纹。没有修改生产事件规则或忽略失败。
