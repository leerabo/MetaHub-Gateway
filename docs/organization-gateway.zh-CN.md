# 组织级网关模型

MetaHub 是“组织控制平面 + 模型数据平面”的一体化 AI Gateway。团队给应用一个受控凭据即可调用多个模型，管理员集中管理厂商凭据、路由、预算、权限和审计。

## 组织层级

```text
组织
  └─ 项目
      └─ 应用
          └─ 虚拟 API KEY
              └─ 对外模型别名
                  └─ 有序模型候选
                      └─ 厂商凭据和端点
```

客户端只拿到 MetaHub Virtual Key，不会拿到 OpenAI、Anthropic、Gemini、Grok 或其他厂商的真实 KEY。Virtual Key 可以绑定项目和应用，设置限流、停用、轮换和审计；应用只能使用组织为它开放的模型别名。

## 一个 KEY 调用多个模型路由

一个应用 KEY 不等于固定一个上游模型。同一个 KEY 可以调用多个组织级模型别名，每个别名都可以指向不同厂商和模型。例如：

| 对外别名 | 候选路由 | 用途 |
| --- | --- | --- |
| `team-chat` | `gpt-6-sol` → `claude-sonnet` → `gemini-pro` | 通用对话 |
| `team-code` | `claude-sonnet` → `gpt-6-sol` | 代码审查和开发 |
| `team-fast` | `gemini-flash` → `gpt-6-luna` | 低延迟、低成本任务 |

客户端只需要一个网关地址和一个 Bearer KEY，在请求中选择组织定义的别名：

```bash
export METAHUB_URL=https://gateway.example.com
export METAHUB_KEY=mhv_your_virtual_key

curl "$METAHUB_URL/v1/chat/completions" \
  -H "Authorization: Bearer $METAHUB_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"team-chat","messages":[{"role":"user","content":"总结这个故障。"}]}'

curl "$METAHUB_URL/v1/chat/completions" \
  -H "Authorization: Bearer $METAHUB_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"team-code","messages":[{"role":"user","content":"审查这个补丁。"}]}'
```

应用不需要知道具体由哪个厂商响应。请求日志会记录请求别名、实际模型、厂商、回退尝试、用量、成本、预算结果和路由解释。

## 管理员配置流程

1. 登记厂商并把厂商凭据保存在控制平面。
2. 添加或发现模型，填写能力和当前输入/输出/缓存价格。
3. 为团队能力创建稳定的模型别名。应用依赖别名，上游模型可以在别名后面更换。
4. 选择路由模式和候选顺序。每条路由有一个默认模型，最多 31 个有序备用模型。
5. 创建项目和应用，添加成员，再把应用 KEY 分配给需要的使用方。
6. 在组织、项目、应用、人员或 KEY 层配置预算和限流。
7. 先测试厂商，再用新 KEY 发一个小请求，确认后邀请成员。

## 路由选择模式

- **固定顺序**：严格按管理员配置的候选顺序，适合必须固定模型的业务。
- **可用性优先**：优先选择健康且符合条件的模型，平局时仍按配置顺序。
- **成本优先**：在可用候选中按当前价格和可比较货币重新计算。缺少价格或货币无法换算时不会把模型当成“免费”，而是回到配置顺序并说明原因。
- **质量 + 成本**：先通过质量门槛和样本数门槛，再综合质量、成本、延迟评分；冷启动和平局规则确定且可解释。

回退是第二层机制：选中模型遇到可重试的厂商或网络错误时，才按别名的备用策略尝试下一个模型。权限、预算、能力和安全拦截发生在厂商调用之前，回退不会绕过这些限制。

## 一次请求如何完成路由

网关会按稳定顺序处理每次请求：

1. 校验 Virtual KEY，并解析它所属的组织、项目和应用范围。
2. 检查请求的别名是否已开放给该应用，以及请求是否符合能力策略。
3. 在访问供应商前，先检查组织、项目、应用、人员和 KEY 的预算与限流。
4. 排除已停用、不健康、不兼容或缺少价格信息的候选模型。
5. 根据别名的路由模式和当前供应商元数据选择候选模型。
6. 调用供应商、记录用量和成本；只有可重试的失败才会按配置尝试备用模型。

客户端只收到一次响应，但审计记录会保留完整路由决策：请求别名、符合条件的候选、实际供应商和模型、回退尝试、延迟、Token 用量、成本，以及预算或策略拒绝原因。管理员因此可以集中调整路由，客户端集成保持稳定，每次选择也都能被复核。

## 治理边界

厂商 KEY 属于组织，永远不会返回给客户端。Virtual Key 是面向人员、项目和应用的受控凭据。停用应用、项目、成员、路由或 KEY 会在网关边界生效。用量和成本按组织层级归集，财务和工程可以从不同视角查看同一请求。

这就是个人中转代理与组织级网关的区别：地址只是数据平面，真正的产品契约是控制平面决定谁可以调用、可以使用哪个别名、哪些模型符合条件、最多花多少钱，以及为什么最终选择这个模型。
