# MetaHub 用户可见模型接入复验

日期：2026-09-11。接续此前 U47..U50，只记录本轮新增发现。

## 方法

使用 computer-use 技能推荐的浏览器接口，先检查实际页面、点击按钮和填写表单，
随后结合接口和代码定位。修复后再从首页提示复走，不把直接跳内部路由作为可发现性证据。
使用既有合成验收账号和“体验验收组织 0910”，未操作用户的业务组织。

## 新发现与修订

- U51：添加模型默认选中已停用服务。只提供明确 active 的服务；单个自动选择，
  多个要求明确选择；没有可用服务时提供有权限的配置入口。加载中与加载失败分别显示。
- U52：路由名称允许先填写中文，但服务端拒绝。名称旁显示简短格式要求，并在字段上
  使用与服务端一致的原生格式校验。单个运行环境自动带入；多个环境在基本表单明确选择，
  不在高级设置中静默选中列表第一项。多个调用模型也不再隐式选中第一项。
- U53：模型和路由提交只有按钮变灰，失败后整页刷新、表单收起、草稿丢失。
  现在按钮立即显示创建状态，提交时冻结输入，确定失败后原位恢复表单并显示中文原因。
  两种创建请求的等待上限为 15 秒，覆盖响应体读取；超时和网络错误标记为“结果未确认”，
  保留输入并要求先刷新列表核对，绝不自动重发写请求。离开组织仍取消请求、拒绝迟到结果。
- U54：登录首屏被迟到的旧默认品牌投影替换标题和颜色。仅兼容字段完全匹配、无图标、
  第一代的旧初始默认品牌；自定义字段或后续已发布版本保持原样，不改历史品牌记录。
- U55：保存服务 KEY 后直接提示配置模型，但接入进度仍要求健康检查，测试入口却藏在
  管理服务中。凭据就绪但未健康时直接显示“测试连接”；健康后才提供模型配置下一步。
  该交接状态通过渲染测试覆盖，本轮没有保存真实厂家 KEY 或进行模型调用。
- U56：按真实用户从公开首页进入注册，等待页面完成初始化后，邮箱、显示名称、密码、
  确认密码、隐私条款和基础验证码均按顺序可见；“注册”文案和密码显示按钮可达。
  服务状态入口可从顶部导航直接打开并返回组件状态，没有再依赖控制台内部路由。
- U57：真实登录后首次进入控制台偶发显示“暂时无法连接组织空间”，需要用户理解并点击
  “重新连接”；控制台现在对 `workspace_session.required`、5xx、网络失败和启动超时自动补偿一次，最终仍保留显式重试。
  “员工与 KEY”首次加载约 8 秒，期间保留“正在加载员工与 KEY...”状态；创建使用者后
  自动展开“发放 MetaHub KEY”，表单只要求姓名和可选部门，没有邮箱、密码或员工注册。
- U58：账号设置的组织空间页只要求空间类型和组织名称，区域、服务模式等技术默认不再
  暴露；登出请求完成前显示“正在退出登录”，成功后回到公开首页，避免先闪出登录表单再跳转。
- U59：复测仍观察到少数首次登录/整页重载会先落到连接恢复页，点击一次“重新连接”后约
  5 秒进入控制台；服务日志对应首次 `workspace/session` 401、随后切换和读取 200。
  这说明还存在前端启动与 Workspace Cookie 建立的竞态，当前记录为剩余缺陷，不能宣称已完全消除。

## 实际浏览器证据

- 修复前实际填写中文路由名，经历无反馈等待后得到英文错误，表单被收起且输入消失。
  独立接口诊断对相同非法名称约 766ms 返回 422，不能把浏览器等待等同于服务端处理耗时。
- 修复后中文名称立即触发字段校验；重复的 company-default 名称得到中文重复提示，
  原输入和展开表单保留，按钮可再次提交。
- 实际创建 ux-visible-route-0911 成功，列表从 1 条变为 2 条；随后仅停用这条验收路由，
  页面明确显示已停用，原 company-default 路由保持启用。没有删除数据。
- 修复版本首次重载出现一次 Failed to fetch；按页面“重试”恢复。此次错误仍是未关闭的
  间歇性连接问题，不能宣称系统全部稳定。
- 最终响应式与首页路径复验结果将在本轮结束前补齐。
